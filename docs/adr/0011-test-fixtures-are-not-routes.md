# 0011. Test fixtures are not routes

- **Status:** Accepted
- **Date:** 2026-09-30

## Context

Two sets of GPX files exist in this repository and they look like the same thing. `routes/` holds
rideable routes with a `manifest.json` entry each; `test/fixtures/` holds GPX files used by the
unit tests and by Playwright.

They are not the same thing, and the directory names do not explain why. The obvious and wrong
move — adding a 30 km route to `test/fixtures/` because it is "for testing", or pointing a test
at a bundled route because it is already there — is one a future contributor will make within a
week of not reading this.

The two have opposite requirements. A rideable route has to be long enough to be worth riding:
20 to 30 km, varied terrain, a profile with something in it. A fixture has to be small enough to
hand-compute an expected value from and fast enough to run in a loop.

You cannot assert against a 30 km profile. Nobody can verify by eye what the grade should be at
18,432 m, so any expected value is whatever the code produced the first time it ran — which makes
the test a change detector, not a correctness check. And a Playwright run that has to ride a
route to completion needs that to take seconds.

## Decision

The two sets stay separate, with different rules.

**`routes/`** — bundled rideable routes, GPX plus a `manifest.json` entry giving id, name,
distance, elevation gain and file. All of them are real places. A GPX drops in and needs nothing
beyond a manifest entry, and an imported route is indistinguishable from a bundled one.

_Amended 2026-10-22._ `routes/` used to hold two synthetic routes generated by a committed
script, each chosen to exercise a code path: near-continuous grade change for the control point
write thresholds, a sustained climb for grade clamping, a fast descent for the zero-power gravity
and drag balance. They were dropped when the app moved to shipping real places only. **The
decision below is unchanged and the paths still need exercising — that job now sits entirely on
`test/fixtures/`, which is the point of this ADR rather than an exception to it.**

**`test/fixtures/`** — small synthetic GPX with exactly computable answers: a 1 km flat, a
constant 10 % climb, a steep descent, a closed diamond loop and a staircase that bends twelve
times. These give exact expected values for the physics, grade, position and map-geometry tests,
and let a Playwright run ride a route to completion in seconds. They have no manifest entry and
never appear in the app's route list.

Two rules for adding one, both learned the hard way:

- **A fixture must bend if the test is about shape.** The original three are all a straight line
  on one meridian, differing only in elevation, which is invisible until a map-projection test
  passes for the wrong reason — or until two of them turn out to have byte-identical coordinates.
- **A fixture's elevation must be monotone or flat.** `despikeElevations` uses a 15-point window,
  so on a fixture short enough to hand-check, a peak halfway along is a minority inside its own
  window and gets flattened: 60 m of declared ascent reads back as 40. The staircase climbs
  10 m a point throughout for this reason, and a loop is flat because it returns to the height it
  left.

**Unit tests use fixtures, with no exceptions.** There used to be one — the test asserting the
generator reproduced its output byte for byte, which necessarily read `routes/`. Both are gone, so
the rule is now absolute: a unit test that opens a file from `routes/` is reaching for a 30 km
profile whose expected values nobody can verify, which is the thing this ADR exists to prevent.

`DESPIKE_THRESHOLD_M` in `src/route/elevation.ts` is the sharpest case. It is tuned under the rule
that a correction must leave known-good data unchanged, and its evidence used to be the generated
routes' exactly-known ascent. It is now `test/fixtures/staircase-24km.gpx`, 360 m by construction.
Nobody can say what Alpe d'Huez's true ascent is, which is precisely why it cannot be the thing a
filter is tuned against.

## Consequences

- Expected values in the physics, grade and position tests are hand-checkable, so a failing test
  means the code is wrong rather than that something moved.
- Playwright rides a complete route in seconds, which is what makes "ride it to completion" a
  test we actually run rather than one we skip.
- Two sets of GPX files is mild duplication, and someone will eventually ask why we do not test
  against the real routes. The answer is above; the generator test is the one place the real
  routes get exercised, and it is deliberately narrow.
- Fixtures are unrealistic by construction. A constant 10 % climb for a kilometre is not a road,
  and nothing about the code's behaviour on real, noisy GPS elevation is proved by them. Real
  routes, the generated ones, and the manual test plan carry that.
- Adding a fixture means asking whether you can still compute the expected answer by hand. If you
  cannot, it belongs in `routes/` and the test needs rethinking.
